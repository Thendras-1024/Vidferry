# PostgreSQL 迁移方案

## 文档状态

- 状态：迁移实现已提供，尚未执行数据切换。
- 当前运行时：未配置 `DATABASE_URL` 时仍使用 SQLite，数据库文件为 `db/database.db`。
- 目标运行时：PostgreSQL 18，使用 Docker Compose 本地部署。
- 本文用于约束后续代码和数据迁移；在迁移验收完成前，现有安装方式与配置保持不变。

当前已实现：

- `docker-compose.postgres.yml`：PostgreSQL 18、本地端口、命名卷和健康检查。
- `db/migrations/postgresql/V001__initial_schema.sql`：初始完整 schema。
- `scripts/migrate_sqlite_to_postgresql.py`：停机前检查、不可变备份、复制和一致性报告。
- PostgreSQL 连接池和 SQLite SQL 方言适配边界。

当前实现保留一个迁移期开关：只有配置 `DATABASE_URL` 才连接 PostgreSQL；一旦配置，连接失败会直接失败，不会回退 SQLite。完成真实数据切换和验收后，再删除默认 SQLite 运行路径。

## 目标与边界

本次迁移解决 SQLite 在后端请求、后台 worker、定时发布和 Agent 并发写入时可能出现的锁竞争，同时保持现有 API、任务状态、账号数据和本地文件引用不变。

目标方案：

- PostgreSQL 官方 Docker 镜像固定主版本 `postgres:18`，补丁版本随镜像更新。
- 应用使用 Psycopg 3 同步连接池访问 PostgreSQL。
- schema 使用顺序执行的版本化 SQL 管理，并在数据库中记录已执行版本。
- 采用停机一次迁移；切换后 PostgreSQL 是唯一主库，不双写，也不自动回退 SQLite。
- 暂不引入 pgvector、Elasticsearch、SQLAlchemy、Alembic 或 LangGraph PostgreSQL checkpoint。

`langgraph-checkpoint-sqlite` 当前只存在于依赖声明中，Agent 持久化实际使用项目自己的会话、消息、运行记录和记忆表。实施迁移时直接移除该未使用依赖，不增加替代 checkpoint。

## 当前基线

2026-07-29 的只读盘点结果如下：

| 项目 | 数值 |
| --- | ---: |
| SQLite 文件大小 | 约 10.8 MB |
| 业务表 | 23 张 |
| 总行数 | 1218 行 |
| Agent 会话 | 9 行 |
| Agent 消息 | 28 行 |
| Agent 运行记录 | 17 行 |

这些数字只用于确认迁移规模。正式停机后必须重新生成实时表清单、逐表行数和校验摘要，不能把本节数字作为迁移验收值。

当前代码包含以下 SQLite 专用行为，迁移不能只替换数据库驱动：

- `PRAGMA`、WAL 和 `sqlite3.Row`。
- `BEGIN IMMEDIATE` 与 SQLite 异常类型。
- `INSERT OR IGNORE`、`rowid` 和 `cursor.lastrowid`。
- `json_extract`、`strftime` 和 `datetime()`。
- `?` 参数占位符。
- 启动时通过 `PRAGMA table_info` 动态补列。

## 目标配置契约

应用只读取一个数据库连接配置：

```env
DATABASE_URL=postgresql://vidferry:<local-password>@127.0.0.1:5432/vidferry
```

Docker Compose 读取以下本地环境变量：

```env
POSTGRES_DB=vidferry
POSTGRES_USER=vidferry
POSTGRES_PASSWORD=<local-password>
```

约束：

- 密码只保存在本地 `.env`，不得写入 Compose、源码、日志或提交记录。
- PostgreSQL 不可用时应用启动失败并明确记录原因，不得静默回退 SQLite。
- Compose 使用命名卷保存 `PGDATA`，配置健康检查，并只向本机暴露端口。
- `.env.example` 已提供配置名；只有执行完迁移并准备切换时才取消 `DATABASE_URL` 的注释。

## 当前执行命令

先安装 Docker Desktop，并在本地 `.env` 设置 `POSTGRES_DB`、`POSTGRES_USER` 和强密码。不要把密码直接写进命令行。

启动 PostgreSQL：

```powershell
docker compose --env-file .env -f docker-compose.postgres.yml up -d
docker compose --env-file .env -f docker-compose.postgres.yml ps
```

后续所有迁移命令都应在 `vidferry` Python 环境中运行。先保持后端正常停止，仅执行只读检查：

```powershell
conda run -n vidferry python -m scripts.migrate_sqlite_to_postgresql preflight --sqlite db/database.db
```

确认 preflight 通过后，在本地 `.env` 配置 `DATABASE_URL`，再执行迁移：

```powershell
conda run -n vidferry python -m scripts.migrate_sqlite_to_postgresql migrate --sqlite db/database.db
```

成功后会生成：

- `db/backups/database-<timestamp>.db`：只读一致性备份。
- `db/postgresql-migration-report.json`：逐表行数、SHA-256、备份路径和备份摘要。

迁移失败时不要执行 `docker compose down -v`，以免删除待核对的 PostgreSQL volume。

## Schema 映射

| SQLite | PostgreSQL | 迁移要求 |
| --- | --- | --- |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 导入时保留原 ID，之后校准 sequence |
| `DATETIME` | `TIMESTAMP WITHOUT TIME ZONE` | 保持当前本地时间文本的墙上时钟语义，不做时区换算 |
| 0/1 整数标记 | `INTEGER` | 暂不改为 Boolean，避免 API 返回类型变化 |
| JSON 文本 | `TEXT` | 保持序列化形式；导入前验证非空值可解析 |
| `REAL` | `DOUBLE PRECISION` | 保留进度等浮点字段语义 |
| `COLLATE NOCASE UNIQUE` | `lower(column)` 唯一索引 | 保持名称大小写不敏感的唯一性 |
| `CURRENT_TIMESTAMP` | `CURRENT_TIMESTAMP` | 列类型仍为无时区时间戳 |

现有外键、唯一约束、检查约束、部分索引和级联删除规则必须逐项复刻。文件路径、Cookie 文件名、任务 ID、视频 ID、JSON 字符串和用户可见文本不得规范化或重编码。

## SQL 改写规则

| SQLite 写法 | PostgreSQL 写法 |
| --- | --- |
| `?` | Psycopg `%s` 参数绑定 |
| `BEGIN IMMEDIATE` | 普通事务；需要互斥时使用行锁、唯一约束或 advisory lock |
| `INSERT OR IGNORE` | `INSERT ... ON CONFLICT DO NOTHING` |
| `cursor.lastrowid` | `INSERT ... RETURNING id` |
| `rowid` 排序 | 使用明确主键和稳定的次级排序字段 |
| `json_extract(text, '$.key')` | 校验后使用 `text::jsonb ->> 'key'` |
| `strftime(...)` | `date_trunc`、`to_char` 或 `extract` |
| `datetime(value)` | 显式 timestamp 比较 |
| `PRAGMA table_info` | 版本化 SQL 与迁移记录表 |
| `sqlite3.Row` | 项目统一的行访问契约，继续支持按列名读取 |

禁止实现通用 SQL 字符串替换器来伪装方言兼容。每条 SQLite 专用查询应在对应业务模块中显式改写并测试。

## 实施阶段划分

### 1. PostgreSQL 基础设施

当前实现包括：

- PostgreSQL 18 的 Docker Compose 服务、命名卷和健康检查。
- Psycopg 3 同步连接池；池大小按 Flask 请求线程和后台 worker 数量设置上限。
- `DATABASE_URL` 配置校验和启动连通性检查。
- PostgreSQL 关闭时释放连接池，避免残留连接阻碍容器停止。

### 2. 版本化 Schema

- 建立 `schema_migrations` 表，记录迁移版本、名称、校验值和执行时间。
- 第一版 SQL 一次性创建当前 23 张业务表、全部约束和索引；生成器只读取 SQLite schema，不读取业务行。
- 后续 schema 修改只能新增顺序版本文件，不再启动时动态检查并补列。
- 每个版本在单个事务中执行；失败时回滚整个版本并阻止应用启动。

### 3. 数据访问改造

- 将连接、事务和按列名读取能力集中到现有 `app/db` 边界。
- 逐处改写 SQLite 方言、异常捕获和自增 ID 获取。
- 保持现有 Flask API 响应字段和数值类型不变。
- 测试使用独立 PostgreSQL 测试库；每个测试隔离事务或重建 schema，不访问迁移后的真实数据库。

### 4. 数据复制工具

迁移工具只读取 SQLite，只写入一个空 PostgreSQL 数据库，并提供 `preflight`、`migrate`、`verify` 三个明确阶段。工具不得修改或删除源 SQLite 文件，也不得输出 Cookie、密钥或完整业务正文。

数据按父表到子表的显式顺序复制。至少遵循以下依赖顺序：

1. 设置、通知、账号、文件记录和其他无外键根表。
2. Agent 会话、规则和记忆。
3. Agent 消息与运行记录。
4. YouTube 分组、视频、检索任务和工作流任务。
5. 检索结果、工作流事件、LLM 用量、字幕审计和发布记录。
6. 定时发布任务及其平台目标。

`agent_session_locks` 与 `youtube_workflow_locks` 是运行时租约/锁表。停机前必须等待相关任务结束，并确认两张表为空；这些临时记录不导入 PostgreSQL。

## 停机迁移步骤

### 1. 迁移前检查

- 通知用户进入维护窗口，停止新的查询、下载、处理、发布和 Agent 请求。
- 等待所有 `queued`、`running` 任务进入终态。
- 停止前端写操作、Flask 后端、定时发布 scheduler 和所有 worker。
- 确认没有残留应用进程写入 SQLite。
- 确认两张运行时锁表为空；不通过时中止迁移，不手工删除活跃锁。

### 2. SQLite 不可变备份

- 使用 Python SQLite backup API 生成一致性备份，不直接复制仍可能打开的数据库文件。
- 对备份执行 `PRAGMA integrity_check`，结果必须为 `ok`。
- 记录源文件与备份文件的大小、修改时间和 SHA-256。
- 将备份放在带时间戳的本地备份目录，不加入 Git，不覆盖原始 `db/database.db`。

### 3. 创建目标库

- 启动健康状态正常的 PostgreSQL 18 容器。
- 要求目标 database/schema 为空；发现已有业务表时中止，不执行覆盖。
- 执行全部版本化 SQL，并验证迁移版本、表、索引、约束和外键已建立。

### 4. 导入数据

- 在受控事务中按依赖顺序复制，显式写入原主键。
- 保留 `NULL`、空字符串、Unicode、换行、时间文本和 JSON 原文。
- 每张表完成后记录导入行数；任何转换或插入错误都回滚本次导入。
- 导入完成后按每张 identity 表的最大 ID 校准 sequence，确保下一次插入不会冲突。

### 5. 数据一致性验证

以下检查全部通过才允许切换：

- SQLite 与 PostgreSQL 的业务表集合一致，明确排除两张运行时锁表。
- 每张表行数、主键集合一致。
- 每张表按主键稳定排序后的规范化行 SHA-256 一致。
- PostgreSQL 所有外键有效，没有孤儿记录。
- identity sequence 的下一值大于当前最大 ID。
- JSON 文本、中文、文件路径和时间字段抽样逐值一致。
- schema 约束、唯一索引、普通索引和级联删除规则与设计清单一致。

迁移工具生成不含敏感正文的本地验证报告，报告至少包含表名、行数、摘要、sequence 和约束检查结果。

### 6. 切换与观察

- 在本地 `.env` 设置 `DATABASE_URL`，执行数据库连通性和 schema 版本检查。
- 先运行自动化测试与只读接口冒烟测试，再启动后台任务能力。
- 完成下方功能验收后才结束维护窗口并恢复用户操作。
- 保留 SQLite 原文件和不可变备份，不删除、不改名，也不让新代码继续写入。

## 回滚规则

在恢复用户操作前发生失败：

1. 停止 PostgreSQL 版应用。
2. 保存 PostgreSQL 容器日志和验证报告。
3. 恢复旧版配置和代码，重新使用原 SQLite 文件。
4. 验证 SQLite 完整性后再恢复服务。

恢复用户操作后 PostgreSQL 已产生新写入时，不允许直接切回 SQLite，否则会丢失新任务、消息和发布状态。此时必须停止写入、保留 PostgreSQL 数据，生成两库差异报告并完成人工增量核对后再决定恢复方向。

迁移失败不得删除 PostgreSQL volume 或 SQLite 备份，直到原因确认且数据核对完成。

## 功能验收清单

### 数据库与并发

- [ ] 启动时只连接 PostgreSQL，连接失败时明确失败且不回退 SQLite。
- [ ] schema 版本检查、事务提交、事务回滚和连接池关闭正常。
- [ ] 并发账号检查、通知同步、任务进度和 Agent 消息写入不再出现 `database is locked`。
- [ ] 唯一约束、外键、部分索引、级联删除和 identity sequence 正常。

### 账号与发布

- [ ] 账号列表、添加、更新、删除和 Cookie 状态检查正常。
- [ ] Cookie 文件路径保持原值，迁移和日志均不读取或暴露 Cookie 内容。
- [ ] 抖音、B站、快手、小红书、视频号即时发布流程正常。
- [ ] 定时发布任务创建、抢占、执行、取消和平台目标查询正常。

### YouTube 与素材

- [ ] 视频检索、单链接导入、分组和重复过滤正常。
- [ ] 下载、转写、翻译、字幕烧录、任务恢复和错误状态正常。
- [ ] 原视频、处理后素材、发布稿、删除记录和发布记录保持完整。
- [ ] 文件系统内容不移动，数据库中的相对/绝对路径不发生变化。

### Agent、通知与统计

- [ ] Agent 会话、消息、摘要、记忆、规则、运行记录和会话租约正常。
- [ ] Agent 并发请求的互斥语义与迁移前一致。

只有同时满足以下条件，才可在 README 和安装文档中把 PostgreSQL 标记为当前运行数据库：

- 全量自动化测试在 PostgreSQL 测试库通过。
- 本文的数据一致性检查全部通过且有本地报告。
- 功能验收清单全部完成。
- 经过并发写入验证，没有 SQLite 锁错误或 PostgreSQL 连接泄漏。
