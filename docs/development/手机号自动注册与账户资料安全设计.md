# 手机号自动注册与账户资料安全设计

## 1. 目标、原则与范围

本设计将 Vidferry 的手机号验证码能力从“仅已绑定账号可登录”扩展为“首次完成手机号验证后自动注册并登录”。腾讯云短信和腾讯云验证码继续分别承担手机号验证和防自动化能力；不接入腾讯云 OAuth 或第三方账号体系。

目标是在不增加独立注册页、不要求设置密码的前提下，达到公网产品的基础账户安全要求：手机号不可枚举，验证码不可重放或并发猜测，账户和资料不可越权，注册不会成为短信、存储或模型资源滥用入口，且认证数据可审计、可轮换、可清理。

首次验证成功时，系统创建一个 `user` 角色账号、绑定 `phone` 身份并建立新会话；已绑定手机号只建立新会话。注册入口位于现有登录页的“手机号登录 / 注册”标签，不新增 `/register` 路由。手机号验证只证明请求时对号码的控制权，不能替代高风险操作所需的二次确认。

本期包含最小个人中心：用户可查看并修改昵称，头像使用前端内置默认头像。`auth_users` 增加可空 `avatar_url`，仅作为未来受控头像存储的预留字段；本期不接受用户上传文件、外部头像 URL 或 `data:` URL。

本期不包含密码设置或找回、手机换绑、头像上传、第三方 OAuth、管理员自助注册、对象存储和公开文件访问。账号注销、资料导出和手机换绑属于后续独立设计；上线前仍必须明确其受理渠道、处理期限和数据处置规则。

## 2. 用户体验与账户规则

### 2.1 单表单流程

1. 用户在同一手机号表单输入手机号，完成人机验证并获取短信验证码；文案明确“首次验证手机号将自动注册”。
2. 前端为一次“发送验证码”操作生成高熵 `idempotencyKey`，仅在当前页面会话中保存；网络超时后以相同键重试，不重复发送短信。
3. 用户输入验证码后提交。成功响应只返回当前会话需要的公开资料和 CSRF Token；仅在已经证明手机号控制权后，才可返回 `isNewUser` 供前端展示一次欢迎提示。
4. 前端不根据手机号前缀、`isNewUser`、角色或本地缓存决定权限。所有权限均以服务端当前会话中的用户身份为准。

验证码表单不展示“该手机号已注册”之类的状态。发送、验证失败、验证码过期、限流和供应商异常都保持统一 JSON 结构；登录成功后的 `isNewUser` 不构成枚举面，因为调用方已完成该号码的短信验证。

### 2.2 账户和资料规则

- 新用户默认昵称为 `Vidferry 用户 000001`，编号为创建后的用户 ID 左侧补零至六位，不包含手机号或其片段。
- 服务端生成仅供内部标识的随机用户名和高熵随机密码。二者不展示、不写入日志、不作为手机号用户的默认登录方式；自动注册用户必须设置 `must_change_password = false`，不得进入不存在的强制改密流程。
- 自动注册账号固定为 `user`，不能由请求字段、前端状态或手机号前缀决定角色。首个管理员仍只能通过现有受控命令创建。
- `displayName` 只接受字符串，服务端去除首尾空白后按字符数限制为 2 至 32；拒绝控制字符、双向覆盖字符和仅由空白组成的名称。昵称按纯文本渲染，前端禁止使用 `v-html`。
- `avatarUrl` 为空时回退前端内置头像。首版 `PATCH /auth/profile` 仅允许修改 `displayName`，服务端拒绝非空 `avatarUrl`、用户 ID、角色、状态、用户名、`isNewUser` 及任何未知字段。
- 用户可使用既有“注销全部会话”能力处理可疑登录。后续接入换绑、密码或发布平台凭据变更时，必须要求近期手机号验证并记录安全审计。

## 3. 接口契约

### 3.1 公开认证接口

| 接口 | 请求和响应 | 必须满足的约束 |
| --- | --- | --- |
| `POST /auth/phone/send-code` | 请求：`phone`、腾讯云验证码票据、`idempotencyKey`。响应：`challengeId`、`expiresIn`。 | 只接受 JSON 请求；先在服务端校验腾讯云验证码，再做手机号和 IP 限流。相同幂等键在有效期内返回原挑战，不再发送短信。不得返回手机号、短信验证码、腾讯云 RequestId 或供应商原始错误。 |
| `POST /auth/phone/login` | 请求：`phone`、`challengeId`、`code`、可选 `remember`。响应：`user`、`csrfToken`、`isNewUser`。 | 仅消费已激活且属于该手机号的挑战；在一个数据库事务内原子消费挑战、查找或创建身份、创建会话和写入审计。失败时不得泄露手机号是否已绑定。 |
| `GET /auth/profile` | 响应：当前用户的资料 DTO。 | 仅认证会话可调用，不加入公开路径。 |
| `PATCH /auth/profile` | 请求：`displayName`。响应：更新后的资料 DTO。 | 必须通过 Cookie 会话、CSRF 和字段白名单校验；目标用户只取 `g.current_user.id`。 |

资料 DTO 固定为 `id`、`displayName`、`avatarUrl`、`role`、`mustChangePassword` 和 `createdAt`。其中 `mustChangePassword` 仅用于维持现有首次改密流程；它不包含 `username`、`passwordHash`、手机号、身份哈希、会话、登录失败次数、锁定时间或最后登录时间。手机号登录响应、`/auth/me` 和个人中心必须复用该白名单 DTO；管理员用户管理可以使用单独的管理员 DTO，不能复用给普通会话。

公开的状态变更接口应拒绝非 JSON 内容类型，并在浏览器请求中校验 `Sec-Fetch-Site`、`Origin` 或 `Referer` 的同源语义；不能以反射 `Origin` 或携带凭据的通配符 CORS 取代该校验。`PATCH /auth/profile` 继续要求 `X-CSRF-Token`。

### 3.2 短信与挑战状态机

短信供应商调用与数据库提交不具备分布式事务，不能依赖“短信发送成功后再插入挑战”的顺序。挑战状态必须为以下之一：`pending`、`active`、`failed`、`consumed`、`expired`。

发送流程如下：

1. 在短事务中取得手机号和 IP 的限流锁，创建 `pending` 挑战，保存验证码 HMAC、手机号身份 HMAC、幂等键 HMAC 和到期时间。
2. 调用腾讯云短信。供应商失败时将挑战标记为 `failed`，不向客户端暴露供应商详情；成功后将该挑战原子标记为 `active` 并返回 `challengeId`。
3. 客户端超时重试时，按幂等键读取同一挑战：`active` 时返回原挑战，`pending` 时给出可重试的统一错误，`failed` 或过期时按限流规则允许新的发送。
4. 同一手机号只能有一个 `active` 挑战；新挑战激活时必须作废旧挑战。过期、失败和已消费挑战由后台清理任务删除。

验证流程必须在一个数据库事务中锁定挑战行。成功路径仅在 `status = active`、未过期、`attempts < max_attempts` 且验证码 HMAC 常量时间匹配时，把状态改为 `consumed`。失败路径也必须使用条件更新或行锁原子增加 `attempts`，并在第五次失败后使挑战不可再用；不得先读出次数再在另一连接写入。事务内对手机号身份取得 PostgreSQL advisory lock，以“查询身份、创建用户、写入身份绑定、创建会话、写安全审计”作为一个原子单元；数据库唯一约束仍是最终裁决。唯一冲突时重新读取既有绑定，不创建第二个用户，也不返回内部数据库错误。

认证响应只在上述事务提交后设置新 Cookie。审计记录使用同一事务写入；审计存储失败应回滚认证事务，避免成功登录没有安全记录。

### 3.3 数据模型与密钥

- 新增递增版本的 PostgreSQL 迁移，为 `auth_users` 添加 `avatar_url TEXT NULL`；已执行迁移不修改。
- `auth_phone_challenges` 增加投递状态、幂等键哈希、激活/失败时间和清理索引。迁移须能安全处理已有挑战表，并为未完成挑战设置明确的过渡状态。
- 继续以 `auth_identities(provider, subject_hash)` 的唯一约束保存手机号身份；手机号明文不得写入数据库。身份哈希使用 `phone:v<key-version>:<hmac>` 格式，使同一唯一约束同时支持轮换期间的旧、新密钥查找。
- 手机号身份 HMAC、短信验证码 HMAC、速率限制 HMAC 必须使用不同密钥或从根密钥按固定用途派生的不同子密钥，不能复用一个 HMAC 密钥。密钥仅由环境变量或密钥管理系统提供，禁止写入代码、迁移、测试夹具和日志。
- 密钥轮换时，新请求以新版本哈希查找，再兼容查询未过期旧版本；成功验证旧版本身份后在受控事务中迁移为新版本。撤销的旧密钥只在所有关联身份完成迁移或经过明确的重新验证窗口后删除。
- 随机内部用户名必须由固定非展示前缀和安全随机值构成，不得从手机号、手机号哈希、昵称或用户 ID 推导。密码哈希仍使用现有 Argon2 配置。
- 会话令牌只存哈希。HTTPS 部署必须设置 `Secure` 并使用 `__Host-` Cookie 名称，Cookie 必须为 `HttpOnly`、`SameSite=Lax`、`Path=/` 且不设置 `Domain`；保留闲置和绝对过期、单会话注销及全会话注销能力。

## 4. 授权、配额与资料生命周期

### 4.1 默认授权和资源防滥用

手机号注册成功不等于无限制使用共享资源。新账号保持 `user` 角色，但必须受服务端配额控制：上传大小与存储总量、上传频率、任务提交频率、并发任务数、每日模型预算和每日短信发送量。配额值由部署配置确定，不写死在客户端；生产启用自助注册前必须为每项设置阈值、拒绝响应和告警阈值。

所有素材、任务、发布账户、Cookie、下载和导出接口必须按当前用户 ID 过滤；新增接口不得依赖前端传入的 `ownerUserId`。发布平台 Cookie 导出默认关闭。跨用户访问统一返回不暴露资源存在性的错误。

异常注册、短信失败率、验证码失败率、同设备或同 IP 的账号创建量、存储和模型消耗必须产生不含手机号明文的监控指标。达到阈值时可暂时冻结该用户的高成本操作，但不自动提升任何角色。

### 4.2 最小化、保留和删除

手机号 HMAC、IP 哈希、User-Agent 和审计记录均按可关联的个人数据处理。数据库不保存明文手机号、验证码、腾讯云票据、Cookie、认证头、密码或腾讯云密钥。

上线前由运维和数据负责人确定并配置保留期限，至少覆盖：过期/失败挑战、速率限制事件、已撤销会话和认证审计。默认建议分别为 24 小时、30 天、30 天和 180 天；清理任务必须可观测、可重试，并记录删除数量而不记录个人标识。账号注销、资料导出和手机号换绑未实现前，不应在产品界面承诺这些能力。

## 5. 威胁模型与防护基线

| 攻击面 | 风险 | 必须落实的防护 |
| --- | --- | --- |
| 短信轰炸、资费滥用 | 反复向手机号或代理 IP 请求验证码 | 每手机号每分钟/每日、每 IP 每小时/每日限流；限流键仅保存 HMAC；幂等重试不重复发送；上线前与腾讯云日限额、费用告警一起复核。 |
| 自动化注册、验证码农场 | 批量绕过前端校验 | 每次发送前由服务端校验腾讯云验证码；票据不可只在前端判断；供应商不可用时拒绝发送，不降级为无验证注册。 |
| 短信投递与网络重试 | 短信已发但挑战丢失，或重试重复收费 | 使用 `pending`/`active` 状态机、幂等键和旧挑战作废规则；供应商响应与客户端超时均可恢复。 |
| 验证码猜测、重放与并发 | 六位验证码被并行提交或重复使用 | 验证码仅保存 HMAC，五分钟过期，最多五次尝试；成功和失败都通过同一事务的条件更新完成；挑战只能消费一次。 |
| 并发注册竞态 | 同一手机号创建多个账号或关联错误账号 | 身份唯一约束是最终裁决；事务内手机号 advisory lock 与冲突后重新读取共同保证单一绑定。 |
| 用户枚举与隐私泄露 | 通过注册流程探测手机号是否存在 | 登录页只表达“登录 / 注册”；未验证前不返回注册状态；日志、审计和分析事件只保留哈希，不记录敏感原文。 |
| 会话劫持、固定会话和登录 CSRF | Cookie 被窃取或用户被诱导登录到攻击者账号 | 登录后始终创建新高熵令牌；Cookie 安全属性、会话过期与注销生效；公开认证接口限制 JSON 和同源浏览器上下文。 |
| CSRF、跨站提交 | 已登录用户被诱导修改资料 | 资料更新强制 CSRF Header；CORS 使用精确来源白名单，禁止反射 Origin 和携带凭据的通配符。 |
| XSS、昵称和头像注入 | 恶意文本破坏界面或执行脚本 | 服务端昵称校验，前端纯文本渲染；首版拒绝头像 URL 与上传；未来头像只允许服务端生成的受控对象键，禁止 SVG 直出和用户可控重定向。 |
| 越权与参数篡改 | 修改他人资料、提升角色、读取他人素材 | 资料目标只取会话用户；忽略请求中的用户 ID、角色和 `isNewUser`；所有业务资源以服务端 owner 过滤。 |
| 共享资源滥用 | 自助注册消耗存储、模型或发布资源 | 服务端按用户实施配额、并发和预算控制；异常模式告警并冻结高成本能力。 |
| 密钥泄露或轮换 | HMAC 密钥泄露后身份不可安全迁移 | 按用途分离密钥、给身份哈希加版本、支持受控双读和迁移；密钥只存部署密钥系统。 |
| 反向代理伪造来源 IP | 伪造 `X-Forwarded-For` 绕过 IP 限流 | 仅当 TCP 对端属于 `VIDFERRY_AUTH_TRUSTED_PROXY_CIDRS` 时读取转发头；公网部署只允许受控反向代理访问后端。 |
| 点击劫持、缓存和内容嗅探 | 登录页或资料响应被嵌入、缓存或错误解析 | 保留 `X-Frame-Options: DENY`、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、HTTPS 下 HSTS；CSP 使用明确的 `script-src`、`connect-src`、`frame-ancestors`，仅加入本应用和腾讯云验证码必需域名。 |
| 数据库与日志泄密 | 原始手机号、验证码、会话或密钥外泄 | 敏感原文只在请求处理内短暂存在；异常和日志不得拼接请求体、认证头、Cookie、`.env` 或腾讯云响应原文；日志字段遵循项目可检索空格规范。 |

## 6. 实现、测试与发布门槛

### 6.1 实现顺序

1. 先将现有“未绑定手机号拒绝登录”测试替换为自动注册的失败测试，再改认证服务；先完成挑战状态机、并发限制、事务和身份创建。
2. 新增 PostgreSQL 迁移，验证递增版本、幂等执行、既有用户的 `avatar_url` 为空及挑战表过渡状态。
3. 实现资料 DTO、`GET/PATCH /auth/profile`、昵称校验和 CSRF 字段白名单，确保普通用户不能修改他人资料、角色或状态。
4. 接入用户资源配额和清理任务，保证注册用户不会绕过素材、任务、模型和 Cookie 的所有权边界。
5. 修改登录页、Pinia 用户状态和用户菜单，保持新老用户同一表单、默认昵称/头像回退和昵称保存后的全局刷新；前端不得持久化验证码、挑战 ID、CSRF Token 或内部用户名。

### 6.2 必须通过的验收

- 新手机号恰好创建一个 `user`、一条 `phone` 身份和一个新会话；并发十次验证同一号码仍只有一个账号和身份绑定。
- 既有手机号不创建用户；验证码过期、错误、第五次失败、重放、并发提交和手机号/挑战不匹配均失败且不泄露绑定状态。
- 短信供应商失败、数据库在供应商成功后短暂故障、客户端超时重试和相同幂等键重试均不会重复发信或留下可用的孤立验证码。
- 所有普通认证响应不包含内部用户名、手机号、哈希、密码、会话哈希、腾讯云 RequestId 或供应商原文；管理员接口与普通资料 DTO 分离。
- 未登录、CSRF 缺失、跨站请求、未知资料字段、伪造用户 ID/角色和跨用户资源访问均被拒绝。
- 新用户配额、异常冻结、挑战/会话/审计清理、密钥轮换双读和旧版本身份迁移均有单元或集成测试。
- 执行认证相关 pytest、PostgreSQL 迁移测试、`npm run build` 和 `git diff --check`。真实腾讯云短信和验证码只在本机审核过的 `.env` 中手工验证，密钥不进入命令、日志、测试夹具或 Git。

### 6.3 灰度、发布与回滚

自动注册必须受独立开关控制，默认关闭；先在受控环境验证，再按部署逐步开启。关闭开关后，已存在手机号账号仍可登录，未绑定手机号恢复为拒绝登录，不删除账户、身份或审计记录。任何短信异常率、注册失败率、资源消耗或安全告警越过上线阈值时，应立即关闭自动注册开关并保留证据用于排查。

功能上线时同步修改 `docs/deployment/用户认证与部署.md` 中“默认不开放自助注册”的说明。公网部署前逐项检查 HTTPS、受信任代理 CIDR、Cookie Secure、精确 CORS 来源、腾讯云短信签名/模板审核、短信限额告警、用户配额、清理任务和自动注册开关。
