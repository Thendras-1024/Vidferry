# 通用模型结构化输出文档

## 1. 文档目的

本文档定义 Vidferry 中需要模型返回结构化结果，且调用方存在解析或校验逻辑的文本和多模态模型调用的统一设计基线。
目标不是让模型“尽量返回 JSON”，而是让业务代码只接收以下两类结果：

1. 已完成安全解析、schema 校验和业务语义校验的模型结果。
2. 契约预先声明、经过独立降级校验并带有明确状态标记的降级结果。

正常自然语言生成不属于本方案，包括 Agent 最终自然语言回复和前端 SSE 逐字显示链路。是否使用本模块取决于调用方是否把模型输出作为结构化数据解析和校验，而不是取决于模型属于文本还是多模态通道。

本文档是设计方案，不代表已经完成代码迁移。当前实现和目标实现分别标记为“现状”和“目标”。

## 2. 背景与问题定义

Vidferry 当前有封面坐标、结构化文案候选、字幕修订、高光审核、内容安全、评论筛选、Agent action、会话标题和摘要等多类由程序消费的 LLM JSON 输出。它们同时具有三种约束：

- **语法约束**：结果必须是合法 JSON，不能是 Markdown、截断文本或自然语言解释。
- **结构约束**：字段名、字段类型、必填字段、枚举、数组数量和额外字段必须符合契约。
- **业务约束**：例如字幕 index 必须与输入完全一致，高光必须落在视频时长内，Agent 工具必须来自白名单，评论 ID 必须来自当前候选集。

这三类约束不能由同一层解决。模型服务端可以约束 token 级语法和部分 JSON Schema；它不能替代本地业务规则，也不能保证模型填入的事实、时间范围或权限参数正确。

### 2.1 现状

当前主要入口是：

- [app/core/llm_harness.py](../../app/core/llm_harness.py)：统一请求、JSON 提取、业务 validator、契约重试、错误分类和 telemetry。
- [app/core/llm_provider.py](../../app/core/llm_provider.py)：OpenAI-compatible provider 识别、`response_format` / thinking 字段和能力探测。
- 业务模块通过 `call_json_contract(...)` 提供 `contract_id` 和 validator。

现有能力已经覆盖：

- `response_format: {"type": "json_object"}` 的 provider 兼容请求。
- 代码围栏、BOM、控制字符、尾逗号和对象提取。
- 业务 validator 的字段、类型、数量、时间轴和安全规则。
- 校验失败后附带错误摘要的一次定向修正请求。
- `empty_content`、`length_truncated`、`json_parse`、`contract_validation` 等错误分类。

现有缺口是：

- 契约主要以手写 validator 表达，没有统一的声明式 schema 来源。
- 没有按 provider 能力选择原生 JSON Schema 或 forced tool call 的统一策略。
- provider 降级后，调用方不一定能清楚知道实际使用的约束层级。
- JSON 修复、schema 校验和业务语义校验的边界没有形成公共接口。
- 文本和多模态调用虽然复用 harness，但契约能力没有独立建模。

## 3. 术语与保证边界

### 3.1 结果状态

| 状态 | 含义 | 能否直接进入业务逻辑 |
| --- | --- | --- |
| `parseable_json` | 文本可解析为 JSON | 不能，仍需 schema 和业务校验 |
| `schema_valid` | JSON 符合声明的 JSON Schema | 不能，仍需业务语义校验 |
| `contract_valid` | schema 和上下文语义校验都通过的模型结果 | 可以 |
| `degraded` | 契约预先声明的 fallback 或通过独立降级校验的结果 | 可以，但调用方必须识别降级状态 |
| `failed` | 任一阶段失败且重试预算耗尽，也没有可用的契约降级 | 不能，必须报错 |

### 3.2 “严格正确”的真实含义

“严格正确”不能被理解为模型永远不会失败。系统能提供的保证分为三层：

1. **服务端约束保证**：支持 constrained decoding 的 provider 可以把非法 token 排除在采样之外，从而保证合法 JSON 和受支持的 schema 结构。
2. **客户端校验保证**：所有结果都必须在本地再次解析和校验，不能信任 provider 的成功标志。
3. **业务语义保证**：由 Vidferry 自己检查输入关联、范围、权限、数量、敏感内容和状态机前置条件。

拒答、`max_tokens` 截断、网络失败、服务商临时不支持参数，以及 schema 合法但值错误，仍然需要应用层处理。`parseable_json` 和 `schema_valid` 只是内部中间状态，不能作为成功结果返回调用方。

## 4. 外部方案对照

### 4.1 Few-shot 与 JSON mode

few-shot 只能改变模型的行为概率，不能在采样阶段禁止非法字符或额外字段。它适合补充字段含义、边界案例和业务示例，不适合作为唯一可靠性措施。

JSON mode 通常只保证返回内容是合法 JSON，不保证字段集合、字段类型或业务关系。DeepSeek 官方要求同时在提示词中说明 JSON、给出示例，并提醒可能返回空内容或因 `max_tokens` 截断；因此普通 `json_object` 应归入“语法约束增强”，不能当作 schema strict。

### 4.2 OpenAI Structured Outputs

OpenAI 的 `response_format.type = "json_schema"` 与 `strict = true` 使用 schema 约束生成，可作为后续 `native_schema` adapter 的实现参考。工具调用也可以通过 `strict = true` 约束参数。官方同时说明拒答和提前中断时可能不符合 schema，且 schema 不能阻止字段值的事实或语义错误。

该能力是未来原生 schema 适配器的参考，不代表首期实现默认启用。服务端结构约束不能替代 Vidferry 的本地 schema 和业务语义校验。

参考：[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

### 4.3 Anthropic 扩展边界

Vidferry 当前没有 Anthropic Messages API 适配器，首期不得把 Anthropic 参数加入现有 OpenAI-compatible 请求链路。文档只保留未来扩展点：若项目后续引入独立 Anthropic adapter，必须单独定义请求、响应、拒答、usage 和错误映射，并经过真实模型验收后才能声明结构化能力。

参考：[Claude Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

### 4.4 DeepSeek

DeepSeek 的普通 JSON Output 使用 OpenAI-compatible 的 `response_format: {"type":"json_object"}`，重点是合法 JSON 字符串。其 strict tool calling 当前属于 Beta 能力，并要求使用 `https://api.deepseek.com/beta` 等专属条件。Vidferry 首期不启用该能力，也不能根据 provider 名称推断 strict 支持；只有具体模型的静态能力配置和真实请求验收都通过后，才能在后续适配器中开启。

参考：

- [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)
- [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

### 4.5 PydanticAI / Instructor 思路

PydanticAI 和 Instructor 的核心价值不是“让模型天然正确”，而是把 Python 类型/schema、解析、验证错误和重试闭环起来。校验错误应以字段路径和期望值的形式反馈给模型，并使用独立且有上限的 output retry budget。

Vidferry 可以借鉴这个协议，不必因此替换现有 LangGraph 或引入完整 Agent 框架。正式实施时必须把当前运行基线 `pydantic==2.13.4` 声明为项目直接依赖，不能继续依赖 LangGraph 的传递安装；所有契约模型必须使用 `ConfigDict(extra="forbid")`。

参考：[Pydantic Configuration](https://pydantic.dev/docs/validation/latest/api/pydantic/config/)

## 5. 目标架构

### 5.1 结构化执行链路

```text
请求 + StructuredContract
    |
    v
具体模型的静态能力配置
    |
    +--> 首期 : json_mode / prompt_only
    |
    +--> 后续已验收 adapter : native_schema / tool_strict
    |
    v
严格 JSON 解析
    |
    v
Pydantic schema 校验
    |
    v
业务 semantic validator
    |
    +--> 成功 : contract_valid + typed result
    |
    +--> 失败 : 通用模块在总预算内定向重试
                    |
                    +--> 成功 : contract_valid + typed result
                    +--> 耗尽 : fail / fallback / soft_accept
```

能力层是单次请求采用的约束方式，不是依次盲目重发的固定流水线。每次请求都必须记录实际使用的 `enforcement_level`，且任何服务端约束都不能跳过本地解析、schema 校验和 semantic validator。

### 5.2 首期：现有 OpenAI-compatible 链路

首期只复用当前 `/chat/completions` 客户端，不新增通用 provider 抽象：

- 具体模型的静态能力配置明确允许时使用 `response_format: {"type": "json_object"}`，记为 `json_mode`。
- 未配置 JSON mode，或服务端明确拒绝该可选参数且契约允许兼容降级时，删除该参数并记为 `prompt_only`。
- 不根据 provider 名称推断能力，不在启动时发送自动探测请求。
- 文本和多模态消息共用契约生命周期；多模态只改变 `messages` 内容，不改变本地校验和失败策略。
- 首期不发送 Anthropic Messages API 参数，也不自动切换到 DeepSeek Beta Base URL。

### 5.3 后续：按模型验收的原生适配器

`native_schema` 和 `tool_strict` 仅作为后续能力保留。启用条件必须同时满足：存在独立请求/响应 adapter、具体模型静态配置明确开启、目标 schema 属于服务端支持子集，并且真实模型验收覆盖成功、拒答、截断和非法参数。

使用 `tool_strict` 时，每次请求只注册一个内部生成的输出工具，强制单工具调用并关闭并行工具调用。从 arguments 提取对象后仍要走完整本地校验，且不得执行这个伪工具。服务端 strict 只覆盖 schema 能表达的结构约束，时间区间、候选 ID、权限和内容安全等规则仍归 semantic validator。

### 5.4 严格解析边界

新模块只容忍 UTF-8 BOM，以及完整包裹单个 JSON 对象的 `json` 或无语言标记代码围栏。以下输入一律判定为 `json_parse`：

- JSON 前后存在非空自然语言或其他内容。
- 存在多个 JSON 对象。
- 顶层是数组、标量或 `null`。
- 依赖尾逗号删除、字段猜测、类型猜测或控制字符删除才能解析。

迁移期间，现有宽松 `extract_json_object` 只服务尚未迁移的调用点。新契约不得调用该兼容解析器，也不引入 `json_repair` 一类激进修复。

### 5.5 校验驱动重试与总预算

校验失败后，不重发完全相同的 prompt，而是只反馈必要的错误路径、期望类型、枚举或数量约束。候选输出必须标记为不可信数据，不能执行、复述或遵从其中的指令。

重试遵守以下规则：

- 通用结构化输出模块是已迁移调用的唯一输出重试责任方。
- 调用点迁移完成并通过等价性验证后，删除其自带的同类结构化输出重试。
- 通用模块不能覆盖的特殊任务可以保留专属重试，但契约必须记录原因；同一失败不得同时由通用模块和调用点重试。
- `max_output_retries` 限制校验驱动重试，传输重试使用独立计数器；两者都计入 `max_total_attempts`、`total_timeout_seconds` 和 `max_total_tokens`。
- 任一总预算耗尽后立即停止请求，并按契约声明的 `failure_policy` 失败或降级。

## 6. 契约模型

### 6.1 Pydantic 作为新契约的 schema 来源

目标实现中，每个通用结构化契约至少包含：

```python
StructuredContract(
    contract_id="subtitle_revision",
    output_model=SubtitleRevision,
    semantic_validator=validate_subtitle_revision_context,
    failure_policy="fail",
    fallback_factory=None,
    degraded_validator=None,
    prompt_version="subtitle-review-v1",
    max_output_retries=1,
    max_total_attempts=2,
    total_timeout_seconds=180,
    max_total_tokens=8000,
)
```

`output_model` 负责生成 JSON Schema、解析为 typed result，并产生带字段路径的 schema 错误。项目必须直接依赖 `pydantic==2.13.4`，所有输出模型统一使用 `ConfigDict(extra="forbid")`，禁止默认忽略额外字段。

`semantic_validator` 负责 Pydantic 无法表达或不应表达的上下文规则，例如字幕 index 与输入一一对应、高光时间落在视频范围、评论 ID 来自当前批次、Agent 工具名属于服务端白名单，以及发布风险等级符合当前策略。

### 6.2 失败策略

`failure_policy` 只允许以下值：

| 值 | 行为 | 返回状态 |
| --- | --- | --- |
| `fail` | 重试或预算耗尽后抛出稳定错误 | 不返回结果 |
| `fallback` | 调用契约预先声明的 `fallback_factory`，并通过 `degraded_validator` | `degraded` |
| `soft_accept` | 对未通过严格语义校验的候选执行独立 `degraded_validator` | `degraded` |

`fallback` 和 `soft_accept` 都必须返回明确的 `fallback_reason` 和 warnings，不得伪装成 `contract_valid`。降级校验失败时按 `fail` 处理，不能返回未校验对象。

### 6.3 Schema 与返回 metadata

目标 schema 使用对象顶层、明确 required 字段和 `additionalProperties: false`。复杂递归 `$ref`、provider 不支持的 union、正则和跨字段规则不得为了服务端 strict 改写业务语义；它们保留在本地校验。Schema 变更必须更新 `contract_version` 或 `prompt_version`，并同步更新 validator 与测试样例。

`call_json_contract` 继续保持“业务结果、usage、metadata”的返回形态，不改变已迁移调用方最终业务字段。metadata 至少包含：

```json
{
  "result_status": "contract_valid",
  "enforcement_level": "json_mode",
  "attempt_count": 1,
  "validation_retries": 0,
  "fallback_reason": null
}
```

`result_status` 只允许 `contract_valid` 或 `degraded`。调用方使用降级结果时必须保留或向其业务状态映射该标记，不能丢弃降级来源。

## 7. 模型能力配置与实际约束层级

每个具体模型通道维护静态能力配置，例如：

```json
{
  "provider": "openai-compatible",
  "model": "model-name",
  "native_json_schema": false,
  "strict_tool_call": false,
  "json_mode": true,
  "vision_supported": false
}
```

能力字段描述模型和 adapter 已确认支持的上限；`enforcement_level` 描述本次请求实际采用的方式，两者不能混用。首期只允许 `json_mode` 和 `prompt_only`，`native_schema` 与 `tool_strict` 仅在后续 adapter 完成真实模型验收后启用。

能力来源只有显式配置和已验收的具体模型能力表。不得根据 provider 名称推断，不执行启动时自动探测，也不得因为一次兼容请求成功就把模型永久标记为 strict。请求中删除可选字段时，metadata 同时记录 `removed_optional_fields`，实际层级必须按降级后的请求填写。

## 8. 失败与错误分类

统一异常建议继续复用 [app/core/errors.py](../../app/core/errors.py) 的 `LLMContractError` 和 `LLMRequestError`，扩展分类而不改变现有公共 API：

| 分类 | 触发条件 | 默认处理 |
| --- | --- | --- |
| `refusal` | provider 返回拒答或安全拒绝 | 不重写成业务结果，按拒答处理 |
| `empty_content` | content 为空且无可用 tool arguments | 有界重试；失败后报错 |
| `length_truncated` | finish reason 表明达到 token 上限 | 可使用更大预算重试一次 |
| `json_parse` | 文本或 tool arguments 不符合严格解析边界 | 携带最小错误摘要重试，不猜测修复 |
| `schema_validation` | JSON 可解析但不符合 Pydantic schema | 携带路径化错误重试 |
| `semantic_validation` | schema 合法但不符合业务上下文 | 携带最小必要错误重试 |
| `http_bad_request` | provider 不接受当前输出参数 | 仅在静态配置和契约允许时兼容降级，并记录实际层级 |
| `network_timeout` | 请求超时 | 仅使用传输重试预算 |
| `network_connection` | DNS、连接或 TLS 失败 | 仅使用传输重试预算 |

解析、Pydantic schema 校验和 semantic validator 必须是三个独立阶段，不得继续把 validator 抛出的 `ValueError` 统一归类为 `json_parse`。重试耗尽后才执行契约声明的 `failure_policy`。未知异常不得包装成笼统的结构化输出错误；必须保留原始异常链并记录 traceback。

## 9. 日志、遥测与安全

每次结构化调用至少形成开始、完成、失败三态事件，推荐字段：

```text
llm structured output started : contract_id = ... | provider = ... | model = ... | enforcement_level = ... | attempt = ...
llm structured output completed : contract_id = ... | result_status = contract_valid | enforcement_level = ... | attempt_count = ... | duration_ms = ...
llm structured output degraded : contract_id = ... | result_status = degraded | enforcement_level = ... | fallback_reason = ... | attempt_count = ...
llm structured output failed : contract_id = ... | error_type = ... | enforcement_level = ... | retry_count = ... | fallback = none
```

每次结构化请求必须在三个位置暴露同一个实际 `enforcement_level`：运行日志、调用返回 metadata 和 `youtube_workflow_llm_usage_events` 用量账本。实施时为用量账本新增专用字段：

```sql
enforcement_level TEXT NOT NULL DEFAULT 'unknown'
```

迁移前的历史记录允许为 `unknown`；迁移后的结构化调用必须写入 `native_schema`、`tool_strict`、`json_mode` 或 `prompt_only`，不得继续写入 `unknown`。`native_schema` 和 `tool_strict` 在对应 adapter 尚未完成验收前不得出现。账本写入失败沿用现有“不阻断主业务”语义，但必须记录带 traceback 的异常日志。

禁止写入：

- 完整 system/user prompt。
- 完整字幕、评论、转写、图片 data URL 或模型原始正文。
- Cookie、密码、Token、API Key、连接字符串和完整凭据路径。

允许写入长度、数量、哈希、脱敏摘要、字段路径、模型名、provider、耗时、token 数量和最终错误分类。新模块不得把模型原始正文写入 telemetry；兼容旧调用的 `rawOutput` 只能留在旧链路，并在迁移完成后删除。

## 10. Vidferry 迁移边界与顺序

### 10.1 不在本方案内

- 不替换 LangGraph。
- 不引入 PydanticAI、Instructor 或新的 Agent 编排框架作为运行时核心。
- 除为 `youtube_workflow_llm_usage_events` 新增 `enforcement_level` 外，不修改其他数据库 schema、任务状态机或公共 HTTP API。
- 不把模型输出变成直接执行权限。
- 不要求所有 provider 同时具备原生 schema strict。
- 不改造正常自然语言调用、Agent 最终回复或 SSE 流式展示。

### 10.2 迁移顺序

1. 在现有 harness 旁新增 `StructuredContract`、严格解析器和静态模型能力配置；直接固定 `pydantic==2.13.4`，并为用量账本新增 `enforcement_level`。保持现有业务结果字段和公共 HTTP API 不变。
2. 先迁移简单契约：封面坐标、会话标题、Agent action、结构化文案候选和字幕修订。
3. 再迁移内容安全和多模态审核，并验证文本与图像消息共用契约生命周期。
4. 最后迁移评论筛选、高光选择和编辑方案等具有批处理、长超时或专属降级语义的任务。迁移前先记录其专属重试和 fallback，完成等价性测试后再决定哪些由通用模块接管。
5. 每迁移一个调用点，删除已被通用模块覆盖的 JSON 提示片段、通用字段检查和重复输出重试，但保留领域 semantic validator 及通用模块无法覆盖的专属重试。
6. 所有调用方迁移完成后，再评估删除 `extract_json_object` 的兼容分支和旧 validator 适配层。

每一步都必须保持：LLM 不可用时现有业务降级和人工确认语义不变；已通过校验的结果字段格式不变；降级结果有明确状态；失败不会被误报为成功；同一失败不会被调用点和通用模块重复重试。

## 11. 离线测试矩阵

### 11.1 协议与范围层

- 首期 `json_mode` 和 `prompt_only` 请求与当前 OpenAI-compatible `/chat/completions` 链路兼容。
- 静态配置没有开启的 `native_schema` 和 `tool_strict` 不得被发送。
- provider 不支持 JSON mode 参数时，只在契约允许且总预算未耗尽时降级为 `prompt_only`，并暴露实际 `enforcement_level`。
- 文本和多模态消息都能通过同一契约入口。
- Agent 自然语言回复和 SSE 流式展示不经过结构化输出模块，现有逐字显示行为不变。
- 后续 adapter 各自测试原生 JSON Schema 请求和单输出 strict tool，不纳入首期必需能力。

### 11.2 解析层

- 接受纯 JSON 对象、UTF-8 BOM 和完整包裹单对象的代码围栏。
- 拒绝前后解释文字、尾逗号、非法控制字符和截断 JSON。
- content 列表、tool arguments、空 content 和 refusal。
- 不接受顶层数组、标量或多个无关 JSON 对象。

### 11.3 校验层

- 缺字段、额外字段、错误类型、非法枚举和数组数量错误。
- `ConfigDict(extra="forbid")` 能拒绝额外字段。
- Pydantic 错误路径能转换为有限 retry prompt。
- semantic validator 能拒绝越界时间、未知 ID、非法工具和不匹配输入索引。
- schema 合法但语义错误时不能直接返回成功。
- `fallback` 和 `soft_accept` 只有通过独立降级校验才能返回 `degraded`，并包含 reason 和 warnings。

### 11.4 重试与失败层

- 输出重试次数严格受限，网络重试与输出重试分别计数，并共同受请求数、总耗时和总 token 预算限制。
- 已迁移调用点不会对同一输出失败叠加外层重试；特殊重试必须有契约声明和独立测试。
- 重试耗尽抛出稳定 `LLMContractError`。
- 拒答、截断、空内容和 HTTP 400 能映射到正确分类。
- 所有失败路径都保留原始异常链，不吞异常。

### 11.5 安全与日志层

- 日志不包含完整 prompt、字幕、模型正文、凭据和图片 data URL。
- 日志、返回 metadata 和用量账本记录一致的 provider、model、contract、attempt、耗时、token、错误类型、结果状态和 `enforcement_level`。
- 历史账本记录可以是 `unknown`，迁移后的新结构化调用不得写入 `unknown`。
- 用户输入和模型候选始终按不可信数据处理，不能通过 retry prompt 获得工具权限。

## 12. 验收标准

文档对应的实施必须满足以下条件：

1. 调用方只能收到严格校验通过的模型结果，或契约预先声明并带有明确状态标记的降级结果；不得静默使用未校验或来源不明的模型输出。
2. 调用方不需要自行决定 provider 兼容降级顺序和失败分类。
3. 每次请求都能从日志、返回 metadata 和用量账本回答“用了哪种结构化约束、尝试了几次、为什么成功、降级或失败”。
4. few-shot 和普通 `json_object` 被明确定位为增强或降级手段，而非 schema 级保证。
5. 文本模型与多模态模型共用同一契约生命周期。
6. 现有 `call_json_contract` 调用方可以分阶段迁移，不要求一次性重写。
7. LLM 服务失败时，现有 Vidferry 工作流继续遵守既有 fallback 和人工确认语义。
8. Agent 正常自然语言回复和 SSE 流式展示不受结构化输出模块影响。
9. 已迁移调用点由通用模块统一负责输出重试，特殊任务只有在通用模块不能满足需求且经过显式声明时保留专属重试。
