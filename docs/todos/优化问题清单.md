## 第一部分:更改区审核(未提交改动)

本次改动主体是新增「内容安全审查(content_safety)」功能 + 继续 PG 重构收尾(清理 BOM)。

### 1. 风险点(更改区)

| # | 问题 | 位置 | 后果 |
|---|------|------|------|
| **C-R1** | **`contentSafetyReviewEnabled` 无 LLM 门禁 → 流水线卡死** | [settings_service.py:81](app/core/settings_service.py#L81)、[workflow_runner.py:489-504](app/core/workflow_runner.py#L489-L504) | `commentBurnEnabled` 有 `and processVersion==... and _comment_burn_available()` 门禁,新增的 content_safety 没有任何门禁。LLM 检测失败时走 `except` 置 `status="unavailable"`,但后续 `if status=="clear"` 不成立就直接落到 `waiting_confirmation`。**只要启用该功能且 LLM 不可用,每个任务都卡死在等待人工确认**,与"不配 LLM 时优雅降级"的项目约定相悖。 |
| **C-R2** | **事务内调 ffprobe 持行锁** | [content_safety_service.py:187-203](app/core/content_safety_service.py#L187-L203) | `BEGIN → SELECT…FOR UPDATE → _get_video_info(子进程) → commit`。ffprobe 耗时数百 ms~数秒,期间持行锁 + 占 PG 连接;ffprobe 卡住会拖垮连接池。应先把 duration/区间算好,**事务里只做快照读写 + 条件 UPDATE**。 |
| **C-R3** | **CORS 回环通配放行写操作** | [setup.py:179-182](app/backend/setup.py#L179-L182) | 新增 `hostname in {127.0.0.1, localhost, ::1}` 即放行跨源写。项目用 Cookie 会话、无 CSRF token,**本机任意端口页面都能向后端发 POST/DELETE**。若被诱导打开恶意本机页面,可静默触发建任务/删账号。建议收窄到已知端口,或对写方法保留白名单。 |
| **C-R4** | **`source-preview` / `downloadCookie` 无鉴权** | [youtube.py:392-400](app/api/youtube.py#L392-L400)、[AccountManagement.vue:485-487](sau_frontend/src/views/AccountManagement.vue#L485-L487) | 路径收敛做得好(`is_relative_to` + `send_from_directory`,无穿越),但整条 youtube 链路无登录校验;`downloadCookie` 下发的是**等同登录凭证的 cookie**。建议补最小鉴权,并显式 `HOST=127.0.0.1` 绑定。 |

### 2. 健壮性差(更改区)

- **C-B1 确认路由把"源视频缺失"返回成 500** — [youtube.py:386-389](app/api/youtube.py#L386-L389):`resolve_content_safety_confirmation` 抛 `FileNotFoundError`,路由只捕 `LookupError/ValueError/WorkflowConflictError`,落入通用 `Exception` → 500。这是可恢复业务态,应是 404/409 + 可读提示。
- **C-B2 显式 `BEGIN`/`commit` 偏离 `_db_connect` 约定** — [content_safety_service.py:187,230](app/core/content_safety_service.py#L187):全代码库**唯一**手动写 `BEGIN` + `conn.commit()` 的地方。`_db_connect` 本就提供隐式事务(success→commit/exception→rollback)。冗余且误导维护者,删掉改 `with _db_connect(row_factory=True)` 即可。
- **C-B3 合并区间后丢 evidence/signals** — [content_safety_service.py:144-149](app/core/content_safety_service.py#L144-L149):`_content_safety_normalize_ranges` 会排序+合并重叠/相邻(0.05s)区间,然后用**合并前的** `(start,end)` 建 `by_range` 索引反挂 evidence。一旦合并,新区间键查不到 → 风险段的 `evidence/signals/riskLevel` 被**静默剥离**,前端只见时间区间无证据。应在合并阶段携带 evidence。
- **C-B4 校验器抛 `TypeError` 而非 `ValueError`** — [content_safety_service.py:106](app/core/content_safety_service.py#L106):`int(item.get("startCueIndex"))`,模型省略字段时 `int(None)`→`TypeError`,跳过了 `call_json_contract` 的契约级重试。
- **C-B5 多段 concat 无超时/上限** — [content_safety_service.py:234-259](app/core/content_safety_service.py#L234-L259):保留段多时 filter_complex 极长易崩;失败只查 `st_size>0`,半成品非零字节但不可播放的情况漏过。
- **C-B6 内容安全阶段在两个 runner 重复** — [workflow_runner.py:550-558](app/core/workflow_runner.py#L550-L558) 与 [:594-603](app/core/workflow_runner.py#L594-L603) 近乎逐行相同;一处改 bug 另一处易漏。应抽 `_run_content_safety_stage`。
- **C-B7 失败日志只记类名** — [workflow_runner.py:491-492](app/core/workflow_runner.py#L491-L492):`error = %s, exc.__class__.__name__`,不记 `str(exc)`/`exc_info`,排障困难。
- **C-B8 前端"标记安全"不预校验** — [SubtitleAudit.vue](sau_frontend/src/views/SubtitleAudit.vue) `confirmSafety`:空原因/空区间直接 POST 撞后端 400。应提交前 `:disabled` 或校验。
- **C-B9 SubtitleAudit 确认按钮显隐偏宽** — 仅判 `jobStatus==='waiting_confirmation'` 未判 `step==='content_safety_confirm'`,会错显按钮最终 409。
- **C-B10 `backend_common` 未知 resource 改抛 ValueError** — [backend_common.py:90-91](app/utils/backend_common.py#L90-L91):从"静默回退 processing"改为 fail-fast 是改进,但需确认所有调用点 resource 字面量都在白名单内(已确认 search/download/processing/analysis/comment 都在,无回归)。

### 3. 冗余设计(更改区)

- **C-D1 executor 选择逻辑 + 硬编码平台键重复** — [youtube.py:377](app/api/youtube.py#L377) 与 [youtube.py:381](app/api/youtube.py#L381) 附近发布确认路由同款 `target = run_youtube_workflow if any(job.get(k) for k in (发布位...)) else ...`。新增平台(如腾讯)两处都要同步。应抽 `_resume_workflow_target(job)`。
- **C-D2 前端 baseURL 拼装两处重复且不一致** — [youtube.js:107-109](sau_frontend/src/api/youtube.js#L107-L109) 用 `${DEV?'/api':''}`,[AccountManagement.vue:485-487](sau_frontend/src/views/AccountManagement.vue#L485-L487) 用另一套带 `VITE_API_BASE_URL` 兜底。应抽公共 `apiBase()`。

- **C-D4 `create_youtube_workflow_job` 先 INSERT 再单独 UPDATE content_risk** — [workflow.py:330-331](app/core/workflow.py#L330-L331):可合并进 INSERT,省一次往返并消除"任务已建但 content_risk 未写"窗口。
- **C-D5 三处各自算 `_render_layout_scales`** — cover/editing/subtitle 三 service 都推导 `round(BASE*scale)`,魔数(493/162/176/99…)散落缺集中常量。

### 4. 功能边界不清(更改区)

- **C-F1 页面改名"内容安全审查"过猛** — [App.vue:73-77](sau_frontend/src/App.vue#L73-L77)、[SubtitleAudit.vue:5-7](sau_frontend/src/views/SubtitleAudit.vue#L5-L7):标题/tooltip 全改,但 4 个 tab 里 3 个仍是字幕修订/评论筛选/LLM 诊断,只有新增"风险裁剪"tab 属内容安全。老用户会找不到字幕审查入口。
- **C-F2 `content_safety_service` 单文件混 DB/LLM/FFmpeg/工作流状态** — 检测、快照读写、人工决议事务、视频裁剪全在一起,而状态机推进(`_run_content_safety_review`)却在 `workflow_runner`。同一生命周期两半分居两模块,裁剪逻辑复用会带出 DB 依赖。
- **C-F3 `jobStatusText` 用 step 反向重载 `waiting_confirmation` 文案** — [YoutubeResearch.vue:2970+](sau_frontend/src/views/YoutubeResearch.vue#L2970):状态语义被 step 污染,再加一种 waiting 又叠分支。应让后端返回显式 `waitingFor` 字段。
- **C-F4 下载 job 设 `processVersion`** — [youtube.py:503](app/api/youtube.py#L503):下载本身无处理版本,语义混乱且会被 translate 覆盖。
- **C-F5 字幕 `BorderStyle` 1→3 等视觉重写缺回归测试** — [subtitle_service.py:946-955](app/core/subtitle_service.py#L946-L955):从"描边+阴影"改成"不透明灰底";cover/editing 尺寸公式全面重写,[cover_service:244](app/core/cover_service.py#L244) 描边下限从 `max(3,..)` 降到 `max(1,..)` 小字号描边仅 1px。无截图/渲染回归兜底。
- **C-F6 评论 `textX` 与头像 `x` 取同值,文字压头像** — [subtitle_service.py:811-816](app/core/subtitle_service.py#L811-L816):`x` 与 `textX` 现完全相等,而头像 overlay 仍按 `layout['x']` 叠加(~101×scale)。旧实现 `textX=margin+avatar+gap`。测试只断言 `overlay=x=43`,没断言二者不重叠。

### 更改区 — 最该优先修的 Top 5

1. **C-R1 内容安全无 LLM 门禁 → 流水线卡死**([settings_service.py:81](app/core/settings_service.py#L81))— 会直接让整条流水线在 LLM 不可用时卡死,最高优先级。
2. **C-R2 事务内 ffprobe 持锁** — 把 `_get_video_info` 与区间归一化移出 `SELECT…FOR UPDATE`。
3. **C-B3 合并区间丢 evidence + C-B2 显式 BEGIN 偏离约定** — 合并阶段携带 evidence;删 `BEGIN`/`commit` 改用 `_db_connect`。
4. **C-F5/F6 烧制视觉重写缺回归** — `BorderStyle 1→3`、评论文字压头像,需对 720×1280/1080×1920/1920×1080 实际渲染人工确认 + 补断言。
5. **C-R3+C-R4 CORS 回环通配 + 文件下发无鉴权** — 本次改动唯一扩大的安全面,收窄端口/补鉴权。

## 第二部分:整个项目审核(架构与系统性)

**总体判断**:业务面扎实(工作流编排、发布去重、评论烧制降级、鉴权层都考虑过真实失败),但工程基底有两块结构性技术债。鉴权层 `app/auth/` 是项目最高质量部分(哈希会话、CSRF、防枚举 dummy hash、双超时、审计),可作为重构参照。

### 1. 风险点(架构级,整个项目)

- **P-R1 命名空间执行单体(根因债)** — [runtime.py:63-77](app/backend/runtime.py#L63-L77) `load_backend_namespace` 把约 40 个模块 `exec` 进同一 globals。`workflow.py`/`workflow_runner.py`/`publish_execution.py`/`subtitle_service.py` 引用几十个**从未 import** 的名字;`globals().get()` 防御式调用 **25 处横跨 8 个 core 文件**(`subtitle_service.py:51` 甚至 `globals().get("backend_logger")`)。后果:
  1. IDE/类型检查全盲,重命名/跳转失效;
  2. **不可单测**(脱离 namespace 无法 import,单测粒度被迫拉到整个后端,叠加 tests/ 多数 gitignore → 核心业务无真正单测);
  3. MODULE_ORDER 顺序即隐式拓扑,换序即 NameError;
  4. 放大所有重构风险(这正是 CLAUDE.md "高风险链路改动要小而明确"的本质来源)。

- **P-R3 迁移系统两缺陷** — [schema.py:28-46](app/db/schema.py#L28-L46):① 按 `;` 切分 SQL(当前 7 个迁移无函数体所以安全,但未来出现 `CREATE FUNCTION` 内含 `;` 即破碎);② 记 checksum 但**不校验**,改已下发迁移不被察觉。
- **P-R4 发布孤儿成功窗口未完全闭合** — [publish_execution.py:249-328](app/core/publish_execution.py#L249-L328) 已做进程级 inflight 注册表 + 关停 terminate + 启动恢复 + 跳过已发布平台(值得肯定)。但注册表是**进程内字典**,硬崩溃/`kill -9`/断电时:孤儿发布子进程仍在跑(不依赖父进程)→ 平台侧上传成功但 `_mark_published` 因父进程已死没写库 → 重启标 failed → 重试时跳过逻辑因无记录不跳过 → **重复上传**。发布是面向真实账号的不可逆操作,重复上传触发风控。
- **P-R5 凭证/启动脆弱性** — [config.py:14](app/config.py#L14) `from conf import BASE_DIR, INTERNAL_CONFIG` **无 try/except**,fresh clone 缺 `conf.py` 时整个 `app` 包 ImportError,错误信息是 "No module named 'conf'" 而非"请复制 conf.example.py";`.env` 加载在 conf import 之后,conf.py 读不到 .env 变量。

### 2. 健壮性差(整个项目)

- **P-B1 无全局错误处理器** — Grep `errorhandler` = **0 处**;**156 处 bare `except`** 横跨 14 个 API 文件(youtube.py 占 56);**32 处手写 `"code":500`**;**12 处 `print()`** 出现在 API 的 except 里。未捕获异常以 Flask 默认 HTML 500 返回,`str(exc)` 裸露给前端(可能含路径/SQL)。
- **P-B2 响应契约三种变体** — `jsonify({code,msg,data})` / `_json_response(...)` / 含 `success` 字段。前端 [request.js:41](sau_frontend/src/utils/request.js#L41) 用 `data.code in 2xx || data.success` + `data.msg || data.message` 双兜底——**前端在替后端擦不一致的屁股**。
- **P-B3 长任务无统一超时/断点续传** — 发布有 3600s 超时(好);下载/转写/FFmpeg/LLM 分析阶段无显式超时;启动恢复只标 failed,**不支持断点续跑**。
- **P-B4 资源管理** — DB 连接池 `close_database_pool` 存在但未见在 shutdown 钩子调用;中间文件(ass/wav/png)清理路径需审计。
- **P-B5 可观测性弱** — `backend_logger` 与 `print()` 混用;无结构化日志/request id;发布结果混在 `published_youtube_materials` 里无统一 trace。

### 3. 冗余设计(整个项目)

- **P-D1 三个死代码 uploader 包** — `uploader/tk_uploader`(TikTok)、`baijiahao_uploader`(百家号)、`xhs_uploader`(旧版小红书,已被 `xiaohongshu_uploader` 取代)仅被 `examples/` 引用,不在平台映射内。`xhs_uploader` vs `xiaohongshu_uploader` 尤其易踩错。建议删除或归档。
- **P-D2 `myUtils/postVideo.py` 完全未使用** — `post_video_DouYin/tencent/ks/xhs` 唯一 import 点是 [setup.py:130](app/backend/setup.py#L130) 的 `=None` 兜底赋值,**0 处真正调用**。实际发布走 `app.publish_runner` 子进程。误导性"看似可用"的死路径。
- **P-D3 三个顶层 utils 目录职责重叠** — `myUtils/`、`app/utils/`、`utils/`(stealth.min.js 等)。建议统一到 `app/utils/`。
- **P-D4 三个入口 + 两条初始化路径** — `run.py` 调 `app.create_app()` → [app/__init__.py:13-19](app/__init__.py#L13-L19) 又 `import_module("sau_backend")` 回到 namespace;`sau_backend.py` 又是兼容入口直接 `load_backend_namespace`。两份恢复逻辑(`run.py` 多一步 `reconcile_finished_workflow_events`)会漂移。
- **P-D5 多平台 main.py 仍偏厚(但重复度比预期低)** — 已抽 `BaseVideoUploader`,四平台继承结构一致(CLI 不重复业务逻辑,值得肯定);残留是每平台上传编排高度相似可再抽模板方法。

### 4. 功能边界不清(整个项目)

- **P-F1 `setup.py` 是装配大杂烩** — [setup.py](app/backend/setup.py) 198 行同时干:导全部库、导 config 几十常量、建 app、配 CORS/CSRF、挂鉴权、optional 导入平台、改 PATH。是 namespace 模式"什么都塞 globals"的必然产物,R1 迁移后应拆成 app 工厂 + security + 各模块自 import。
- **P-F2 core 逆向依赖 namespace** — `app/core/*` 本应只依赖 db/config/utils,现状还依赖"被 exec 注入的兄弟函数",职责边界被 namespace 模糊。
- **P-F3 CLI ↔ uploader 是隐式契约** — CLI 与 publish_runner 都 import uploader 的具名符号,无抽象接口,uploader 改名/改签名同时打断两处。应让 uploader 暴露稳定入口函数。
- **P-F4 素材库与处理流耦合在路径硬编码** — [publish_execution.py:86-87,459](app/core/publish_execution.py#L459) 直接拼 `BASE_DIR/videoFile/...`,表记录与磁盘文件两套真相源,文件被外部移动会到发布子进程里才报错。应统一过 `material_service.resolve_path()` 并发布前预校验。
- **P-F5 前后端职责:后端契约未集中** — 见 P-B2,SSE 通道与 axios 通道的鉴权/CSRF 各写一份。

### 整个项目 — 最该优先改善的 Top 5(架构层面)

1. **P-R1 偿还命名空间单体债(根因)** — 立"新代码必须显式 import"红线,逐模块把 `globals()` 隐式依赖改真实 import,`globals().get` 改默认值。不解决它,单测、IDE、安全重构都无从谈起。
3. **P-B1+B2 全局错误处理器 + 统一响应契约** — 成本低收益大,注册 `@app.errorhandler` + `api_ok/api_fail` helper,清理 32 处手写 `code:500`/12 处 `print()`,顺带不再裸露 `str(exc)`。
4. **P-R4 闭合发布孤儿窗口** — 发布不可逆,优先级高于其他健壮性项;前置持久化"即将发布"记录 + 子进程成功后独立短事务标记 + 启动恢复对账。
5. **P-D1+D2+D4 清理死代码与多入口** — 删 3 个死 uploader 包 + `myUtils/postVideo.py` 死导入,收敛 `run.py` 唯一入口。直接降低 R1 迁移工作量,是 Top1-2 的前置动作。
